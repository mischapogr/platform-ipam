# SCALE-1 local ledger contention baseline, 2026-10-14

This is a synthetic PostgreSQL ledger measurement, not a customer workload or
an end-to-end API, NetBox, discovery, or reconciliation qualification. No AWS
service was called. SCALE-1 remains open.

## Fixture and method

`TestMeasurePostgresLedgerContention` in
[`internal/storage/measure_contention_test.go`](../../internal/storage/measure_contention_test.go)
runs only with `IPAM_MEASURE=1` and an isolated loopback
`IPAM_TEST_DATABASE_URL`. It creates and drops its own PostgreSQL schema. The
fixture has 1,000 committed synthetic allocations, 1,000 completed operations,
1,000 idempotency records, five findings and 10,000 audit events. Each client
uses its own ledger connection pool. Twenty serial operations per client are
started together: seven update one allocation and thirteen read the state.
The final read confirms that every client's updates persisted. The measured
duration includes transaction setup, the global advisory lock, state loading,
diff persistence and commit; it excludes seeding and final verification.

The run used source commit `ee9a65d` plus this new test in the worktree, an
isolated `postgres:17.5-alpine` container, and the pinned
`golang:1.26.9-bookworm` image on an 8-CPU x86_64 host. Image IDs were
`sha256:deedec4d7fe463f0d7dac743340b1f6ebc12fdf788510ab616dbe6da9e1d9c1e`
and `sha256:6880d90c0623e6e55560894ff82266f5a06c0f7b1c9ee7f6e2def900d9bc2956`,
respectively. The database used a temporary loopback port and was removed
after the run. No existing development volume was changed.

| Clients | Operations | Updates / reads | Elapsed | Median | p95 | Maximum | Throughput |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 20 | 7 / 13 | 1,011 ms | 38 ms | 89 ms | 91 ms | 19.76 ops/s |
| 4 | 80 | 28 / 52 | 4,505 ms | 225 ms | 379 ms | 428 ms | 17.76 ops/s |
| 8 | 160 | 56 / 104 | 7,040 ms | 331 ms | 565 ms | 792 ms | 22.72 ops/s |

The test passed in 15.11 seconds, including fixture creation and final checks.
These are one-run observations; the p95 is a sample quantile, not a service
objective. The rising per-operation latency with more clients is consistent
with contention on the existing global ledger lock, but this run does not
isolate that lock's time from state decoding, PostgreSQL, or host scheduling.

## Reproduction and next gate

Use a disposable PostgreSQL 17.5 database on loopback and the pinned Go 1.26.9
image. Set `IPAM_TEST_DATABASE_URL` to that database and `IPAM_MEASURE=1`, then
run `go test -mod=readonly -buildvcs=false -run
'^TestMeasurePostgresLedgerContention$' -v ./internal/storage` inside the Go
container. The opt-in test refuses a non-loopback database and creates a unique
schema; the database itself must be disposable and managed separately.

Before setting a capacity claim or changing the lock design, the owner must
specify representative allocation, operation and audit counts; concurrent
read/write arrival rates and mix; account/domain distribution; acceptable p95
latency; and the target PostgreSQL/NetBox topology. Then measure actual API
reservations, discovery and reconciliation together in that environment.
This ledger-only baseline does not replace the prior 1,000-allocation NetBox
pass measurement in [ADR 0017](../decisions/0017-PERSISTING_ONLY_WHAT_A_LEDGER_TRANSACTION_CHANGED.md).
