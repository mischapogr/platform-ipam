---
name: onboarding-import
description: Import existing AWS accounts, networks and IP ranges from CSV, TSV, Excel or pasted tables into NetBox occupancy and configuration fragments.
---

Read [onboarding import](../../../docs/ONBOARDING_IMPORT.md), [AWS organization inventory](../../../docs/AWS_ORGANIZATION_INVENTORY.md), [ADR 0007](../../../docs/decisions/0007-ONBOARDING_IMPORT_AS_UNMANAGED_OCCUPANCY.md), [overlap assessment](../../../docs/OVERLAP_ASSESSMENT.md) and [ADR 0014](../../../docs/decisions/0014-RESOURCE_AWARE_OVERLAP_ASSESSMENT.md), and, for giving an imported network an owner, [ADR 0010](../../../docs/decisions/0010-ADOPTING_EXISTING_NETWORKS_AS_ALLOCATIONS.md) and the [adoption runbook](../../../deploy/runbooks/ADOPTION.md).

- **Before deciding what to import**, `platform-ipam onboard assess --inventory inventory` reports which VPC CIDR associations in the same inventory directory conflict with each other -- offline, no NetBox credentials, collapses nothing (unlike `plan` below, which collapses overlapping rows into one write for the allocator's sake). See [overlap assessment](../../../docs/OVERLAP_ASSESSMENT.md).
- **For a reviewed `migration.yaml`**, `platform-ipam onboard progress --plan migration.yaml --inventory inventory --allocations evidence.json` (evidence.json from `platform-ipam client evidence`) derives per-move progress facts, never a percentage or a "done" -- see [Migration progress](../../../docs/MIGRATION_PROGRESS.md) and [ADR 0015](../../../docs/decisions/0015-REVIEWED_MIGRATION_PLAN_AND_DERIVED_PROGRESS.md).
- Imported networks become NetBox prefixes in the domain's VRF without platform allocation markers (`platform_allocation_id`, `platform_allocation_key`, `platform_operation_id`, `platform_state`); they occupy space, never allocations.
- NetBox writes go through the adapter's `EnsureOccupancy`, never raw HTTP from the command.
- A duplicate CIDR in one VRF, a row equal to a configured pool, and a row containing a pool are errors because they break `Snapshot` and `chooseCIDR`.
- An incomplete inventory snapshot is not an empty one. `plan` refuses it, because every "already present" and "overlaps managed" check would otherwise pass vacuously.
- `plan` runs before `apply`, and `apply` refuses to run if `plan` reported any error.
- Accounts are configuration fragments only: `render-config` prints YAML for human review and merge, never edits files. Changing `cloud_coverage` requires advancing `coverage_generation`, which invalidates absence evidence ([AWS integration](../../../docs/AWS_INTEGRATION.md), section 3). `IPAM_IDENTITY_FILE` replaces the identity list wholesale; the `subject` field in rendered identities is a placeholder for human replacement.
- `inventory/` output is never committed and contains sensitive account and network data.
- No consumer API endpoint may be added for import: no endpoint selects a CIDR or mutates pools ([API v1](../../../docs/API_V1.md), section 2). The import is an operator process mode, not a `client` verb.
- Adoption is a separate process mode, `platform-ipam adopt plan|apply`, not part of `onboard`: it opens the ledger and needs the cloud observer, which `onboard` never does. Leaving an imported network as unmanaged occupancy is a valid end state — adopt only what a tenant needs under platform management. Full procedure, prerequisites and refusal codes: the [adoption runbook](../../../deploy/runbooks/ADOPTION.md).

Use `platform-ipam onboard assess|parse|plan|apply|render-config|render-fixture` for the workflow (`assess` first, optionally, then the import steps). `scripts/aws/org-inventory.sh` collects the networks table by assuming a read role into every active member account; `failures.csv` must be empty or explained before its output is imported. Exit codes (both `assess` and the import steps): 0 ok, 2 usage, 3 validation (bad input, plan/apply error, or -- `assess` only -- a report that is not clean), 4 adapter (configuration or NetBox failure, or -- `assess` only -- no report exists at all). Run the Go tests in the pinned image (`docker run --rm -v "$PWD":/src:ro -v ipam-gomod:/go/pkg/mod -w /src golang:1.26.8-bookworm go test ./internal/onboard/... ./internal/onboardcmd/... ./internal/netbox/... ./internal/assess/...`), `tests/aws/test_org_inventory.sh` and `tests/aws/test_assess_from_inventory.sh` (or `scripts/ai/check-aws`), and `./tests/e2e/run-e2e.sh` for anything that touches the import or the adapter: two defects in this feature passed every test against a fake NetBox and appeared only against a real one. None of this proves a run against a live AWS Organization or the handling of a real Excel or LibreOffice file, and `adopt` is demonstrated end to end against the development stack only (`tests/e2e/test_e2e_adopt.py`): a VPC without subnets, and a VPC with one subnet in the two runs the runbook describes.
